# 設計書テンプレート運用ガイド

> プロジェクト全体の文書分類、SSOT、Frontmatter、ライフサイクルは [`docs/README.md`](../../README.md) を正本とします。本書はBD/DD/DSテンプレート固有の選択方法・記入規約を定義します。

## 1. ドキュメントの分類とテンプレート選択

作成する設計書の目的に応じて、以下のテンプレートの中から最適なものを選択してください。

| 分類                 | テンプレートファイル           | 正本範囲              | 主な記述内容・適用目的                                                                         |
| :------------------- | :----------------------------- | :-------------------- | :--------------------------------------------------------------------------------------------- |
| **基本設計書**       | `TEMPLATE_基本設計書.md`       | `system_architecture` | システム全体の目的、アーキテクチャ方針、コンポーネント分離、システム境界、依存関係の定義       |
| **詳細設計書**       | `TEMPLATE_詳細設計書.md`       | `module_behavior`     | 特定モジュール・関数の入出力 DTO、状態遷移・シーケンス、エラーハンドリング、単体テスト要件     |
| **データ構造仕様書** | `TEMPLATE_データ構造仕様書.md` | `persistent_data`     | 永続化スキーマ (DAO/State正本)、状態タクソノミー、配置ディレクトリ、原子置換契約、排他制御仕様 |

> 本リポジトリでは設計の骨格となる `BD` (基本設計)、`DD` (詳細設計)、`DS` (データ構造) の3種を公式テンプレートとして提供しています。環境、運用、テスト、ADR、要求、分析、レビューなどは、全体分類を [`docs/README.md`](../../README.md) で管理し、個別テンプレートは対応するIssueで追加します。

### 利用手順

1. 文書の責務に合うテンプレートをコピーし、命名規則に従って新しいファイル名を付ける。
2. Frontmatter、本文、Mermaid図、改訂履歴の順に記入する。
3. `document_role`、`ssot_scope`、`status`、`owner`を対象文書に合わせて設定する。
4. 関連文書の文書番号と相対リンクを設定し、SSOTの境界を相互に確認する。
5. 作成完了チェックを実施し、Mermaidを含むMarkdownとしてCI検証を通す。

## 2. 機械可読メタデータ (YAML Frontmatter) と記法標準

### ① YAML Frontmatter の適用範囲と正本一元管理

AIアシスタントや自動化スクリプトがドキュメント属性を正確かつ高速に抽出できるよう、**本テンプレートから新規作成する設計書**の先頭に YAML Frontmatter を配置します。プロジェクト全体のFrontmatter規約は [`docs/README.md`](../../README.md) とし、本書では設計書で必須となる値を示します。

```yaml
---
title: "基本設計書"
document_type: "basic_design"
document_number: "[PROJECT_PREFIX]-BD-[NUMBER]"
document_role: "normative"
ssot_scope: "system_architecture"
status: "draft"
version: "1.0"
created_at: "YYYY-MM-DD"
updated_at: "YYYY-MM-DD"
author: "[作成者 / チーム名]"
owner: "[責任者 / チーム名]"
purpose: "[この文書の目的]"
related_documents:
  - "[PROJECT_PREFIX]-DD-[NUMBER] 詳細設計書正本（相対パス: ./...）"
  - "[PROJECT_PREFIX]-DS-[NUMBER] データ構造仕様書正本（相対パス: ./...）"
---
```

| キー                        |   必須   | 設計書での形式・制約                                                           |
| :-------------------------- | :------: | :----------------------------------------------------------------------------- |
| `title`                     |   必須   | 文字列。本文の文書名と一致させる                                               |
| `document_type`             |   必須   | `basic_design` / `detailed_design` / `data_structure_specification` のいずれか |
| `document_number`           | 条件付き | 形式設計書では必須。軽量文書では `source_issue` などで識別する                 |
| `document_role`             |   必須   | 設計書では `normative` を使用する                                              |
| `ssot_scope`                |   必須   | `system_architecture` / `module_behavior` / `persistent_data` のいずれか       |
| `status`                    |   必須   | 初版は `draft`。レビュー後に `review`、承認後に `approved`へ更新               |
| `version`                   |   必須   | 文字列。`MAJOR.MINOR` 形式を基本とする                                         |
| `created_at` / `updated_at` |   必須   | `YYYY-MM-DD` 形式。`updated_at` は `created_at` より前にしない                 |
| `author`                    |   必須   | 初回作成者または作成チーム                                                     |
| `owner`                     |   必須   | 内容の責任者または責任チーム                                                   |
| `purpose`                   |   必須   | この文書の適用目的。テンプレートの説明文を残さず、対象を具体化する             |
| `related_documents`         |   必須   | 文字列の配列。各項目に文書番号・文書名・同一リポジトリ内の相対パスを含める     |

- **二重管理の防止方針**: Frontmatterは文書属性の正本です。文書番号、版数、状態、日付、作成者、責任者などを本文直下の表として再掲しません。本文には、Frontmatterに存在しない固有の情報だけを記載します。
- **SSOT範囲**: `document_role`は文書の役割、`ssot_scope`はその文書が正本とする情報領域を示します。定義は [`docs/README.md`](../../README.md) と [`CONTEXT.md`](../../../CONTEXT.md) を参照してください。
- **関連文書の参照形式**: `related_documents`の各項目は、`[文書番号] 文書名（相対パス）`の形式を基本とします。未作成の文書は作成後に番号とリンクを更新してください。
- **日付フォーマットの統一**: YAML内および本文中の全日付表記は、ハイフン区切りの **`YYYY-MM-DD`** 形式に統一します。

### ② 図表・状態遷移表現の標準化 (Mermaid 記法)

Markdown内でテキスト描画・ネイティブレンダリングを可能にするため、視覚表現にはMermaid記法 (`mermaid`) を標準として使用します。

- **全体構造・データフロー**: `flowchart TD` または `graph TD`
- **状態遷移ロジック**: `stateDiagram-v2`
- **モジュール間シーケンス対話**: `sequenceDiagram`
- **データ構造・エンティティ間関係**: `erDiagram` または `classDiagram`
- 1つの図には1つの主目的を持たせ、対応する本文または表を正本として明記する。
- テンプレートのサンプル名・仮の状態・仮の閾値を実案件の記入後に残さない。
- Mermaidコードフェンスと有効な図本体を維持し、CIの構文・レンダリング検証を通す。

## 3. データ境界ルール (DTO と DAO / 永続化のSSOT分離)

データ管理の混同と関心事の崩壊を防ぐため、データ表現を以下の責務に基づいて明確に分離します。

| データ種別                           | 担当レイヤー                             | 正本ドキュメント          | 定義内容                                                                               |
| :----------------------------------- | :--------------------------------------- | :------------------------ | :------------------------------------------------------------------------------------- |
| **DTO (Data Transfer Object)**       | モジュール間・関数間・ノード間パッシング | **詳細設計書 (DD)**       | 関数の引数、戻り値、イベントパケット、ノード間パッシングパラメータの型・バリデーション |
| **DAO / 永続化スキーマ (State正本)** | ストレージ・ファイル保存・永続化         | **データ構造仕様書 (DS)** | ディスクに物理保存されるJSON/DB構造、状態タクソノミー、原子置換・FileLock排他制御      |

- BDは全体方針・責務・境界、DDはモジュール制御・DTO・状態遷移、DSは永続化データ・保存状態を正本とする。
- 要求、環境、運用、テスト、ADR、分析、レビューはそれぞれの正本範囲を持ち、BD/DD/DSの定義を上書きしない。
- 正本の定義と参照文書が矛盾した場合は、編集日の新しさではなく、`ssot_scope`の正本を更新して整合させる。

## 4. 命名ルール方針 (Naming Conventions)

文書種別とファイル名の管理方法は、形式文書と軽量文書で分けます。

### 形式文書

設計書など、長期的に正本として管理する文書には、次の形式を使用します。

```text
[PROJECT_PREFIX]-[TYPE_CODE]-[NUMBER]_[DOCUMENT_TITLE].md
```

- **`PROJECT_PREFIX`**: 各プロジェクトで定義する識別コード（例: `SBOS`, `APP`, `CORE`）
- **`TYPE_CODE`**: `BD`、`DD`、`DS`など、文書種別に対応する短いコード
- **`NUMBER`**: 同一プロジェクト・同一`TYPE_CODE`内で重複しない連番
- **`DOCUMENT_TITLE`**: 文書内容を表すタイトル

例:

```text
APP-BD-001_基本設計書.md
APP-DD-001_認証詳細設計書.md
APP-DS-001_データ構造仕様書.md
```

形式文書では、Frontmatterの`document_number`、本文の文書番号、ファイル名の番号を一致させます。

### 軽量文書

Issue記録、簡単な分析、レビュー記録などは、形式文書の連番を必須にしません。Issue番号、タイトル、`source_issue`などで追跡できれば十分です。

例:

```text
ISSUE-007_テンプレート整備.md
認証機能の調査メモ.md
ログイン機能レビュー.md
```

### ADR

ADRは`ADR-001_<TITLE>.md`形式を基本とします。既存の`001-document-governance-and-ssot.md`のような命名は、既存文書として維持し、新規文書から新形式を適用します。

TYPE_CODEと`document_type`の正式な対応表、採番範囲、候補種別は [`docs/README.md`](../../README.md) を参照してください。

## 5. 参照規約・非コード化・改訂履歴追跡

### ① 特定環境依存ハイパーリンク (`file:///...` 等) の禁止

- 特定マシンのローカル絶対パスの直接埋め込みは禁止。プロジェクトのポータビリティを保つため、標準文書名テキストまたは同一リポジトリ内の相対パスリンクを使用すること。

### ② 具象ソースコードの非掲載

- プログラムコードの直接貼付は禁止。パラメータ表、データ型、バリデーション制約、事前・事後条件、失敗契約をテキスト・テーブル・Mermaid図で定義すること。

### ③ 改訂履歴 (チェンジログ) の追跡メカニズム

- 仕様の変遷と「なぜその設計・ルールへ変更されたのか」のコンテキストを維持するため、全設計書の末尾に **改訂履歴テーブル** を設置し、変更理由を明記すること。

## 6. 作成完了チェック

- [ ] 形式文書では、ファイル名、本文の文書番号、Frontmatterの `document_type` と `document_number` が一致している。
- [ ] `document_role`、`ssot_scope`、`status`、`owner`を文書の内容に合わせて設定した。
- [ ] `created_at`、`updated_at`、本文の日付が `YYYY-MM-DD` 形式になっている。
- [ ] `related_documents` に文書番号・文書名・相対パスが設定されている。
- [ ] `[ ... ]`、`YYYY-MM-DD`、サンプルのコンポーネント名・状態名・閾値が未置換のまま残っていない。
- [ ] Mermaid図の構文検証を通し、図と本文・表の正本関係を確認している。
- [ ] DTOとDAO/永続化の責務境界および関連文書への参照が明確である。
- [ ] 絶対パス、機密情報、具象ソースコードを本文へ掲載していない。
- [ ] 最終変更の理由を改訂履歴へ記録している。
