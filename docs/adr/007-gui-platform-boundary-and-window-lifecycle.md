# ADR-007: GUI のプラットフォーム依存処理の境界とウィンドウのライフサイクル

| 項目           | 内容                |
| :------------- | :------------------ |
| ステータス     | accepted            |
| 決定日         | 2026-10-26          |
| 決定者・承認者 | tray-translate team |
| 置換元ADR      | なし                |
| 関連Issue      | #85, #80, #56       |

## 1. 背景・課題

ADR-006 は「コードは OS に依存しない形で書き、OS 固有の処理は境界に閉じ込める」と定めた。一方、`crates/gui` のトレイとホットキーの扱いには、次の課題がある。

- **背景**:
  - タスクトレイ常駐（`tray-icon`）とグローバルホットキー（`global-hotkey`）は OS ごとに挙動が違う。
  - Linux（Wayland / GNOME 標準など）では、トレイの初期化が成功してもアイコンが表示されない環境がある。このとき「×ボタンで隠す」とウィンドウへ戻れなくなる。
  - 現状の `app.rs` は、トレイの有無（`self.tray.is_some()`）を「×ボタンの扱い」と「トレイに隠すボタンの表示」の 2 か所で別々に判定している。
  - GUI は `default-members` に含まれず、Linux CI では検査されない（#53）。
- **要求・制約**:
  - Windows の既存動作（トレイ常駐、ホットキー呼び出し）を変えない。
  - ADR-002 は Linux GUI を配布しない。ADR-006 は「配布はしないが、コードは移植可能に保つ」と解釈している。
- **判断しない場合の影響**: 設定やトレイ条件を足すたびに、分岐が `app.rs` の複数箇所へ増える。Linux で終了できないリスクも残る。

## 2. 決定

### 2.1 保証の範囲

- Linux GUI は、**ビルドと基本動作を壊さないこと**までを保証する。トレイの動作保証はしない。
- 本件は機能追加ではなく、挙動を変えない境界整理（リファクタリング）として扱う。ただし 2.3 の既定値は新しい挙動である。

### 2.2 方式: `cfg(target_os)` と Cargo feature の併用

| 用途                 | 方式                                          | 例                                                        |
| :------------------- | :-------------------------------------------- | :-------------------------------------------------------- |
| OS 固有の違い        | `#[cfg(target_os = "...")]`                   | フォント候補、`SystemRoot` の参照、トレイ利用の既定値     |
| 機能を切り離せること | Cargo feature（`tray`、`hotkey`。既定は有効） | Linux CI で `--no-default-features` により GUI を検査する |

- feature は `tray` と `hotkey` の 2 つに限定する。検証する組み合わせは「すべて有効」と「すべて無効」の 2 通りとする。
- `tray` feature が無効のとき、`tray.rs` はモジュール単位で切り替える。`TrayManager::new()` が常に `Err` を返すスタブを置き、`app.rs` に `cfg` を持ち込まない。

### 2.3 ウィンドウのライフサイクル

- 「トレイを使うか」を設定項目（仮称 `use_tray`）として追加する。
- 既定値は OS で分ける。Windows は `true`（トレイ常駐）、Linux は `false`（×ボタンで終了）。
- ヘッダーの「終了」ボタンは、トレイの有無にかかわらず常に表示する（脱出経路を残す）。

### 2.4 判断の置き場所（純粋関数）

トレイの有無で変わる振る舞いは、`app.rs` に分岐を散らさず、egui に依存しない純粋関数にまとめる。トレイ用のトレイト（`TrayBackend`）やダミー実装は作らない。

```rust
pub enum CloseAction {
    HideToTray,
    Quit,
}

pub fn on_close_requested(use_tray: bool, tray_active: bool, is_quitting: bool) -> CloseAction;
pub fn can_hide_to_tray(use_tray: bool, tray_active: bool) -> bool;
```

- `HideToTray` になる条件は `use_tray && tray_active && !is_quitting` のみ。
- 判断の表（設定、トレイの有無、終了中の組み合わせ）を単体テストで網羅する。

### 2.5 グローバルホットキー

- feature として切り離せるようにする。
- ウィンドウの終了判断には関与させない。初期化に失敗しても通常ウィンドウとして動く現在の動作を維持する。

### 2.6 対象外

- macOS（Tier 2）の対応は本件に含めない。ウィンドウを閉じてもプロセスが維持され、Cmd+Q で終了する標準のライフサイクルとの整合は、macOS 対応の Issue で扱う。
- トレイ用のトレイト（`TrayBackend`）の導入。実装が 2 種類以上になる見込みが出た時点で再評価する。

### 2.7 Linux での GUI 検査

- 作成者の Linux 環境で、次のコマンドがすべて成功した（2026-10-26）。

  ```bash
  cargo clippy -p tray-translate-gui --all-targets --locked -- -D warnings
  cargo test -p tray-translate-gui --locked
  ```

- この結果は作成者の環境のものである。CI の `ubuntu-latest` で同じ結果になるかは未確認で、追加のシステムライブラリが必要になる可能性が残る。
- そのため、次の順で進める。
  1. Ubuntu の CI に GUI の `clippy` と `test` を追加し、通ることを確認する。
  2. 通った場合は、`default-members` への復帰を検討する。
  3. 通らない場合は、不足しているライブラリを CI に導入するか、現状（Windows のみで検査）を維持するかを決め、本書に追記する。
- `--no-default-features`（`tray` と `hotkey` を無効にした構成）の検査は、feature の追加後に行う。

## 3. 理由・代替案

### 採用理由

1. OS 固有の違いは `cfg(target_os)` が直接的に表現でき、機能の切り離しは feature が適している。目的が違うため併用する。
2. 判断を純粋関数にまとめると、`app.rs` の重複した条件を 1 か所にでき、設定の追加時に直し漏れが起きない。egui なしでテストできる。
3. 初期化の成否だけでなく設定でトレイの使用を決めると、「初期化は成功したがアイコンが見えない」環境でも終了できる。

### 代替案

| 代替案                             | 利点                        | 欠点・リスク                                                                     | 採用しなかった理由                                                      |
| :--------------------------------- | :-------------------------- | :------------------------------------------------------------------------------- | :---------------------------------------------------------------------- |
| `cfg(target_os)` のみ              | 実装が直接的                | Linux CI で機能の有無を切り替えた検査ができない                                  | 検査の自由度が低い                                                      |
| Cargo feature のみ                 | CI で組み合わせを検証できる | OS 固有の既定値やパスの違いを feature で表すと組み合わせが増える                 | OS 固有の差は `cfg` のほうが適している                                  |
| `TrayBackend` トレイトとダミー実装 | 差し替えが明示的            | 「ダミーなら×で終了」の判断が残り、結局 `is_active()` 相当が必要。コードが増える | 判断を 1 か所に集める効果が純粋関数と同じで、現段階の抽象化に見合わない |
| トレイの初期化の成否だけで判断する | 設定項目が増えない          | アイコンが見えない環境で、隠したウィンドウに戻れない                             | Linux で終了不能になるリスクを防げない                                  |
| macOS も本件で対応する             | 一度に整理できる            | Tier 2 であり、検証環境がない                                                    | 範囲を絞る                                                              |

## 4. 影響・トレードオフ

- **利点**: 分岐が 1 か所になり、トレイ関連の追加が安全になる。Linux でも終了不能にならない。feature により、将来 Linux CI で GUI を検査できる可能性が開く。
- **欠点・コスト**:
  - 設定項目（`use_tray`）が増える。`crates/app` の `Settings` と設定画面の変更が必要になる。
  - `tray` feature の無効時に使うスタブ（約 10 行）を保守する。
  - feature の組み合わせの検査が増える（2 通りに限定して抑える）。
- **影響を受ける正本文書**:
  - 設定ファイルの構造を定義した文書（DS）。`use_tray` の追加時に更新する。
  - `docs/test/gui-manual-test-guide.md`（トレイを使わない設定での動作を追加）。
- **移行・ロールバック**: 既存の設定ファイルに `use_tray` が無い場合は、OS ごとの既定値で読み込む。設定の削除と feature の無効化で元の挙動に戻せる。
- **セキュリティ・運用上の影響**: 通信や権限の変更はない。
