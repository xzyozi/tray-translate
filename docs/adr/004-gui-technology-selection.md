# ADR-004: 常駐 GUI の技術選定（egui / eframe の採用）

## 1. 背景・課題（コンテキスト）

### 1.1 常駐 GUI の必要性

tray-translate は、日常的な作業フローを阻害しない「軽量かつ即応性の高いオフライン翻訳体験」を目標としている。
CLI ツール（`tt`）による翻訳はスクリプト実行やターミナル作業に適しているが、Web ブラウジングや文書作成・エディタ操作中のユーザーがテキストを翻訳する場合、以下の課題がある：

- 翻訳のたびにターミナルを開いてコマンドを入力・実行する必要があり、思考の流れが中断される。
- クリップボードの内容をシームレスに取得し、翻訳結果をワンキーで再コピー・貼り付けするような即時操作が難しい。

これらを解消するため、タスクトレイに常駐し、グローバルホットキーまたはトレイアイコン操作によって瞬時にポップアップして翻訳を行う常駐 GUI が不可欠である。

### 1.2 検討された選択肢

プロジェクト初期のロードマップ（#1）では「Tauri v2 + TypeScript」を想定していたが、正式決定ではなくスパイク調査（#31）を実施した。以下の4案を比較検討した：

- **案A: Tauri v2 (WebView / TypeScript)**:
  Rust バックエンド + Web フロントエンド構成。美麗な UI を迅速に構築可能。
- **案B: Tauri v1**:
  旧世代の Tauri。長期的な保守性や新規機能追従に懸念あり。
- **案C: ネイティブ UI (egui / eframe + 関連クレート)**:
  Rust の即時モード GUI（Immediate Mode GUI）を採用し、OS の低レベル描画 API で直接描画する構成。
- **案D: Windows のみ GUI 提供、Linux は CLI のみ**:
  Linux での GUI 提供を断念する案。

### 1.3 Linux Tier 1 (Rocky Linux 8.10) における webkit2gtk-4.1 欠如問題

ADR-002 では、対象プラットフォームの Tier 1 として **Windows 10 / 11** と並び、**Linux（RHEL 8系 / Rocky Linux 8系互換、glibc 2.28 基準）** を定めている。企業環境やサーバー派生ディストリビューションを含む幅広い Linux 環境で、単一バイナリによる可搬性と完全オフライン動作を保証するためである。

しかし、Tauri v2 の Linux 実装は公式の前提条件として `libwebkit2gtk-4.1`（WebKitGTK 4.1）を要求する。
調査の結果、以下の重大な制約が判明した：

1. **公式リポジトリおよび EPEL での提供状況**:
   RHEL 8 / Rocky Linux 8 系（および AlmaLinux 8 系）の公式リポジトリおよび EPEL には `webkit2gtk-4.1` が提供されておらず、旧来の `webkit2gtk3`（WebKitGTK 4.0 相当）のみが存在する。
2. **方針との衝突**:
   Tauri v2 を採用した場合、Rocky Linux 8 系で GUI バイナリを起動できず、ADR-002 で定めた「Tier 1 サポート」および「単一バイナリでの可搬性」を満たせない。
3. **AppImage への同梱の非現実性**:
   WebKitGTK は巨大なブラウザエンジンであり、これを AppImage などのバンドル形式でまるごと配布することは、バイナリサイズの大幅な肥大化（数百 MB 超）を招き、さらに glibc の依存バージョンが新しくなることで Rocky 8 系の glibc 2.28 と衝突するリスクがある。

### 1.4 オフライン完結性、常駐メモリ、起動速度の評価

| 評価軸 | 案A: Tauri v2 | 案C: ネイティブ UI (egui / eframe) |
| :--- | :--- | :--- |
| **Linux Tier 1 互換性** | 不可（Rocky 8 に `webkit2gtk-4.1` なし） | **良好（OpenGL / X11 / Wayland で動作）** |
| **外部ランタイム依存** | 大（OS の WebView / WebKitGTK 必須） | **極小（グラフィックスドライバのみ）** |
| **配布形態** | 単一バイナリだが特定 shared library を要求 | **完全な単一バイナリ（自己完結）** |
| **完全オフライン性** | 良好（ローカル assets をバンドル可能） | **極めて良好（外部通信コードなし）** |
| **常駐時メモリ消費** | 中〜大（WebView プロセスで 60〜150MB+） | **極小（20〜40MB 程度で待機可能）** |
| **コールド起動速度** | やや遅い（ブラウザエンジンの初期化コスト） | **極めて高速（即座にウィンドウ描画）** |
| **UI 表現力・装飾** | 極めて高い（HTML / CSS / Web エコシステム） | 必要十分（シンプルなツール UI 向き） |

常駐型ツールとしての「軽量常駐（ADR-002）」、および Rocky 8 互換性を総合的に評価すると、Tauri v2 の採用は ADR-002 の前提方針と両立しない。

## 2. 決定内容

### 2.1 ネイティブ UI (egui / eframe) の採用

GUI フレームワークとして、Rust ネイティブの即時モード GUI ライブラリである **`egui`** およびそのアプリケーションシェル **`eframe`**（現行版 0.36）を採用する。

- 外部の巨大な WebView / WebKit エンジンに依存せず、プラットフォームの低レベルグラフィックス API（OpenGL / DirectX 等）を用いて自己描画を行う。
- これにより、Rocky Linux 8 を含む Linux 環境および Windows において、外部大型ランタイムなしで単一バイナリとして動作可能とする。
- Windows 実機において `crates/gui` による翻訳ウィンドウの実装および日本語表示・翻訳・クリップボード連携の正常動作を確認済みである（Issue #34, PR #37）。

### 2.2 独立クレート化とルート `default-members` からの除外

GUI 実装は、ワークスペース内の独立クレート **`crates/gui`**（パッケージ名: `tray-translate-gui`、実行バイナリ名: `tt-gui`）として管理する。

さらに、ルートの `Cargo.toml` において `crates/gui` を **`default-members` から除外**する：

```toml
[workspace]
members = [
    "crates/app",
    "crates/core",
    "crates/cli",
    "crates/gui",
]

default-members = [
    "crates/app",
    "crates/core",
    "crates/cli",
]
```

- **理由**:
  1. `eframe` の依存関係（約300パッケージ）によるワークスペース全体の `Cargo.lock` やビルド時間の肥大化を、コアおよび CLI 開発から切り離す。
  2. GitHub Actions などのヘッドレス CI 環境（Ubuntu 等）において、GUI 固有のシステムグラフィックライブラリ（X11 や Wayland 開発ヘッダ等）の要求によって CI ビルドやテスト（`cargo test --locked` 等）が失敗するリスクを排除する。
  3. GUI のビルドや実行は、画面環境のある開発機で `cargo run -p tray-translate-gui` のように明示的に指定して実行する運用とする。

### 2.3 システム連携ライブラリ

- **クリップボード連携**: `arboard` クレートを採用。テキスト翻訳用途に限定し、不要な画像処理ライブラリの引き込みを防止するため `default-features = false` で利用する。
- **フォント読み込み**: egui の既定フォントは多言語（日本語等）グリフを含まないため、起動時に OS のシステムフォント（Windows では `msgothic.ttc`, `meiryo.ttc` 等、Linux では標準的な日本語フォント）を動的に検索して `egui::FontDefinitions` に登録する方式を採用する。

## 3. 結果と影響

### 3.1 メリット

1. **ADR-002（プラットフォーム方針）の遵守**:
   WebKitGTK 4.1 のような Rocky Linux 8 で入手不可能な共有ライブラリへの依存を排除し、Windows および Linux Tier 1 環境で確実に単一バイナリとして動作する。
2. **軽量常駐と低リソース消費**:
   常駐時の待機メモリが極めて小さく、バックグラウンドで常に動作していてもユーザーの作業環境を圧迫しない。
3. **起動の即応性**:
   WebView のプロセス起動オーバーヘッドが存在しないため、ホットキー押下時のウィンドウ表示が極めて高速である。
4. **技術スタックの統一**:
   フロントエンドに TypeScript / Node.js ツールチェーンを導入せず、コア（CTranslate2 ラッパー）、CLI、GUI のすべてを単一の Rust ツールチェーンで保守・完結できる。

### 3.2 トレードオフと対応策

1. **UI デザインの自由度・表現力**:
   - *課題*: HTML / CSS に比べると、複雑な装飾、リッチなアニメーション、自由なレイアウトには制約がある。
   - *対応策*: 本ツールの目的は「テキストの選択・翻訳・コピー」を即時に行うユーティリティツールであり、視認性と即応性が最重要である。egui の標準ウィジェットで目的を十分に達成可能である。
2. **多言語フォントの自前組み込み**:
   - *課題*: ブラウザエンジンのように OS の多言語フォントフォールバックが自動では行われない。
   - *対応策*: OS のシステムフォントを検索して動的に読み込む初期化処理を `crates/gui` に実装し、Windows 実機で日本語が文字化けなく描画されることを確認済み。
3. **依存パッケージ数の増加**:
   - *課題*: `eframe` の追加により約310の依存パッケージが導入される。
   - *対応策*: `crates/gui` を `default-members` から除外し、CI およびコアライブラリ開発への影響を局所化する。

## 4. 今後の課題・後続タスク

1. **eframe 機能フラグの軽量化検証**:
   現在の既定機能には `wgpu` バックエンドが含まれる。これを `glow`（OpenGL）のみに絞り、`wgpu` を除外することでビルド時間・バイナリサイズ・常駐メモリをさらに削減できるか検証する（Issue #31 残項目）。
2. **タスクトレイ常駐とグローバルホットキーの実装**:
   `tray-icon` クレートによるタスクトレイ最小化・メニュー表示、および `global-hotkey` クレートによる画面外からのショートカット呼び出し（例: `Alt + T`）を統合する（Issue #33, #34）。
3. **Linux 実機 / ヘッドレス環境でのビルド確認**:
   Rocky Linux 8.10 実機において `tray-translate-gui` のビルドに必要な最小限の X11 / OpenGL 開発パッケージを特定し、ビルド手順を整備する。
