# ADR-001: 文書ガバナンスとSSOT

- **ステータス**: Accepted
- **決定日**: 2026-10-02
- **決定対象**: `docs/` 配下の文書分類、正本、メタデータ配置
- **関連Issue**: [#2 BD/DD/DSの責務境界とSSOTを確定する](https://github.com/xzyozi/DEFAULT_PROJECT/issues/2)

## 1. 背景

現在の公式テンプレートは基本設計書（BD）、詳細設計書（DD）、データ構造仕様書（DS）で構成されている。一方、要求、環境、運用、テスト、判断理由、レビューなどの文書を追加すると、どの文書が何を正本とするか、メタ的な管理情報をどこに置くかが曖昧になる。

また、テンプレート固有のREADMEだけに全体ルールを置くと、設計以外の文書へ同じルールを適用しにくい。

## 2. 決定

### 2.1 メタ情報の配置

- プロジェクト全体の文書分類、SSOT、ライフサイクル、Frontmatter、ディレクトリ用途は `docs/README.md` を正本とする。
- プロジェクト用語の定義はルートの `CONTEXT.md` を正本とする。
- 文書ごとの属性は各Markdown先頭のYAML Frontmatterを正本とする。
- テンプレート配下のREADMEは、そのテンプレート固有の使い方だけを定義する。
- Issueコメントは議論・確定に至る履歴、ADRは判断理由を記録する。現在の仕様は正規文書で確認する。

### 2.2 正本範囲

- BD: システム全体のアーキテクチャ、責務、境界、横断方針（`system_architecture`）
- DD: モジュール制御、関数契約、DTO、状態遷移、エラー処理（`module_behavior`）
- DS: 永続化スキーマ、保存状態、移行、原子書き込み、排他制御（`persistent_data`）
- 要求・機能仕様: 実現すべき目的、要求、受け入れ条件（`requirements`）
- 環境仕様: プラットフォーム、言語・ランタイム、ツール、ビルド、CI、再現性（`environment`）
- 運用手順: 起動停止、監視、ログ、復旧、ロールバック（`operation`）
- テスト・レビュー: 検証結果と証跡（`test_evidence` / `review_evidence`）
- ADR: 判断理由、選択肢、トレードオフ、後継判断（`decision_rationale`）

### 2.3 矛盾時のルール

下位文書は上位方針を具体化できるが、正本に反してはならない。矛盾が見つかった場合は、編集日やIssueコメントの新しさだけで決めず、次の手順で解決する。

1. どの情報領域の正本かを確認する。
2. 正本側の要求・設計・制約を更新する。
3. 参照文書、手順、テスト、レビューを更新する。
4. 判断理由やトレードオフがある場合は、ADRとIssueへ記録する。

## 3. 影響

### 利点

- 文書種別が増えても、正本範囲と参照方向を追跡できる。
- Frontmatterの構造を文書間で統一できる。
- IssueやADRの履歴と、現在の仕様を分離できる。
- 特定言語やツールに依存しないテンプレートを設計できる。

### トレードオフ

- `docs/README.md`、`CONTEXT.md`、各文書のFrontmatterを更新する管理コストが増える。
- 文書を追加する際、`document_type`、`document_role`、`ssot_scope`を決める必要がある。
- 将来的に文書一覧を自動生成する場合は、Frontmatterの検証処理が必要になる。

## 4. 代替案

### テンプレートREADMEだけに全ルールを置く

設計テンプレートだけでは、要求・運用・テスト・レビュー文書へ適用する全体ルールを表現しにくいため採用しない。

### Issueコメントだけを正本にする

Issueは議論履歴としては有用だが、現在の仕様を検索・参照する正本としては不十分なため採用しない。

### 中央の文書台帳だけを正本にする

台帳は一覧性に優れるが、仕様本文とメタ情報を二重管理しやすいため、まずは各文書のFrontmatterを正本とする。機械的な一覧が必要になった場合に、Frontmatterから台帳を生成する。
